\chapter{System design and implementation}
\label{ch:system-design-and-implementation}

This chapter describes the design and implementation of the RAG-based AI assistant integrated with Sovelia Core.

The implementation is presented as a practical architecture for an on-premises PLM environment and is connected to the research questions outlined in Chapter~\ref{ch:introduction}. The design reflects the literature review (Chapter~\ref{ch:literature-review}) and the context and constraints described in Chapter~\ref{ch:research-methodology}.

The chapter covers the system architecture, data model, documentation pipeline, retrieval flow, and user interface integration.

\section{RAG system architecture}
\label{sec:rag-system-architecture}

The RAG system architecture was designed to operate within Sovelia Core's existing infrastructure while maintaining compliance with data governance requirements. A layered approach was used to separate concerns and support maintainability.

The design prioritizes foundational RAG capabilities using pre-trained models over approaches requiring extensive infrastructure or domain-specific fine-tuning \parencite{herediaalvaroAdvancedRetrievalaugmentedGeneration2025, shejutiExtendedAbstractEnhancing2025}. Since this is an initial implementation of AI functionality within Sovelia Core, simple and robust design choices were favored to allow for focus on domain specific implementation instead of focusing on cutting edge RAG strategies. Main focus on the implementation is to solve the challenges faced when integrating a RAG system into Sovelia Core.

\subsection{System overview}
\label{subsec:system-overview}

The implemented system follows a layered design aligned with Sovelia Core's architecture and deployment constraints. It consists of data persistence (PostgreSQL with vector search support), an embedding pipeline (documentation processing and embedding generation), business logic (retrieval and response orchestration), API services (secure endpoints), and presentation (a chat UI integrated into the PLM interface).

This separation keeps integration effort low and supports maintainability, as components can evolve without changing the whole system. The design aligns with practical lifecycle management concerns discussed in RAGOps literature \parencite{KimothiAbhinav2025ASGt}. \subsection{Database schema design}
\label{subsec:database-schema-design}

The data persistence layer leverages PostgreSQL with the pgvector extension \cite{PgvectorPgvector2025} to support similarity search over embeddings. This choice primarily reflects the constraint of using Sovelia Core's existing PostgreSQL infrastructure, avoiding an additional vector database component and the operational overhead of synchronizing data across systems \parencite{herediaalvaroAdvancedRetrievalaugmentedGeneration2025, shejutiExtendedAbstractEnhancing2025, taipalusVectorDatabaseManagement2024}. Sovelia Core's database management has been centered around PostgreSQL from it's inception and these databases have long history of reliability in production use. The schema design follows standard PostgreSQL practices for integrity and operational robustness, but also integrates well with pre-existing Sovelia Core database schemas and overall design.

The schema stores configuration parameters, source document metadata, and embedded content chunks. Source types (internal PLM documents, vendor documentation, and web-based knowledge articles) are represented explicitly to preserve their origins. Cascade deletion makes sure that removing a source document cleans up its associated chunks. Version metadata is used to avoid re-processing unchanged external sources. This is particularly useful with internal PLM documents, since those already include revisioning by default.

Figure~\ref{fig:database-schema} shows the complete database schema including the relationships between tables, foreign key constraints, and the enumerated source types. The diagram also highlights the cascade deletion behavior and the vector indexing strategy employed for efficient similarity search.

\subsection{Indexing strategy}
\label{subsec:indexing-strategy}

Retrieval operations usually run on each user query, so indexing is required for predictable latency. Vector similarity search uses a Hierarchical Navigable Small World (HNSW) index \cite{malkovEfficientRobustApproximate2016} with cosine distance, following pgvector guidance \parencite{PgvectorPgvector2025} and common practice in documentation RAG systems \parencite{zhongHoneyBeeEfficientRolebased2025}. Additional indexes support document-level maintenance operations and conversation history queries. These are added to speed up replacing the old versions of certain documents along with their associated chunks and chat history fetching respectively.

\subsection{Access control integration}
\label{subsec:access-control-integration}

Access control was treated as a primary risk area in the third research question (RQ3, Quality \& Risk), because the assistant must not expose information that a user cannot access through the standard PLM interface. The implementation therefore integrates with Sovelia Core's existing rather comprehensive access control model and enforces permissions during retrieval, so that all unauthorized content is filtered out on database level before it reaches the language model \parencite{jeongPermissionAwareRAGIdentity2025, zhongHoneyBeeEfficientRolebased2025}.

For internal PLM documents, each chunk links to its originating document, and the database retrieval function evaluates user-specific access rules as part of the query. This database-level filtering reduces the risk of information leakage and avoids post-processing that can harm recall or waste computation \parencite{zhongHoneyBeeEfficientRolebased2025}. External vendor documentation is treated as globally accessible, reflecting its different governance boundary \parencite{jeongPermissionAwareRAGIdentity2025}. These choices align with enterprise governance and trust concerns highlighted in manufacturing and PLM contexts, but also in the EU AI Act \parencite{wangArtificialIntelligenceProduct2021, sillbergEUAIAct2025}.

\subsection{Provider abstraction layer}
\label{subsec:provider-abstraction-layer}

To keep deployment options flexible within an on-premises PLM setting, an abstraction layer was implemented for both chat (LLM) and embedding providers. The goal was to decouple Sovelia Core integration from provider-specific SDKs and configuration formats, reducing the cost of switching providers as models and enterprise constraints evolve \parencite{opara-martinsCriticalAnalysisVendor2016, wangLargeLanguageModel2025}. Given the rapid pace of model evolution \parencite{maslejArtificialIntelligenceIndex2025a}, vendor lock-in would risk obsolescence. The abstraction layer therefore leaves model and provider selection to the customer, enabling runtime changes to suit evolving requirements and capabilities.

The abstraction layer supports four provider types: OpenAI \cite{APIPlatformOpenAI}, Azure OpenAI \cite{mrbullwinkleWhatAzureOpenAI}, Groq \cite{GroqFastLow2025}, and Ollama \cite{Ollama}. Although these providers use different configuration parameters and authentication mechanisms, the abstraction layer exposes a uniform interface to the rest of the system. Configuration strings in database follow a simple \texttt{provider:model-name} format, which enables runtime changes through the Sovelia Core administration UI. The abstraction layer parses these strings and instantiates the correct provider with the required credentials and endpoint URLs.

Separate abstractions exist for chat models and embedding models, as different providers may be preferred for these distinct workloads. For example, Ollama may be selected for embeddings to prioritize data residency, while Groq may be used for chat completion to prioritize response speed.

Figure~\ref{fig:provider-abstraction} illustrates the provider abstraction layer showing how different LLM and embedding providers are integrated through common interfaces, enabling flexible deployment strategies. \texttt{AIChat} and \texttt{AIEmbeddings} implement provider abstractions and can be used directly elsewhere in source code regardless of the underlying configuration.

\section{Documentation pipeline design}
\label{sec:documentation-pipeline-design}

The documentation pipeline transforms source material into searchable embeddings. It follows a four-stage flow (acquisition, chunking, embedding, storage), consistent with practical implementations reported in comparable RAG integrations \parencite{herediaalvaroAdvancedRetrievalaugmentedGeneration2025, shejutiExtendedAbstractEnhancing2025}.

Documentation is ingested from three sources: internal PLM documents (stored inside the Sovelia Core server), Sovelia release notes retrieved via Umbraco \parencite{UmbracoCMSDocumentation2025, ReleaseNewsAll}, and Sovelia Help articles retrieved via the Document360 API \parencite{Document360API, SoveliaHelp}. Internal PLM documents are processed automatically and immediately when they change, while external sources are refreshed on a schedule.

For internal PLM documents, the system maintains a queue of documents requiring vectorization. When users upload or modify documents matching configured criteria, the PLM system enqueues the document for processing. The embedder processes queued documents asynchronously, ensuring timely updates without continuous polling of the entire document base. This event-driven design aligns with the core PLM principle of maintaining accurate, current product information throughout the lifecycle \parencite{starkProductLifecycleManagement2015}: stale embeddings would undermine the assistant's value just as stale product data undermines PLM itself.

External Sovelia release notes and Sovelia Help articles are both retrieved with REST APIs, although different ones. Document360 API offers automatic versioning of articles, which are then used to incrementally update the documentation index, but on the contrary Umbraco lacks this ability, so on refresh, all of the articles are automatically re-processed.

\label{subsec:pipeline-orchestration}
Documents are split into overlapping chunks before embedding. The chunk size (2000 characters) and overlap (200 characters) balance retrieval precision with sufficient local context \parencite{herediaalvaroAdvancedRetrievalaugmentedGeneration2025, shejutiExtendedAbstractEnhancing2025, LangChainOverview}.

Each chunk is transformed into a vector embedding using a 768-dimensional embedding model (Nomic \,\texttt{nomic-embed-text}) \parencite{NussbaumZach2025NETa, CuiPeng2019ASoN}. The chunk content is converted to and stored in Markdown format to preserve semantic structure as this formatting is suggested by OpenAI as a best practice for prompt engineering \parencite{openaiPromptEngineeringOpenAI}. The pipeline itself combines scheduled refreshes for external sources with event-driven processing for internal PLM document changes. Failures processing individual documents are logged without interrupting processing of other documents to now clog the system under heavier loads.

Embedded chunks are stored with source metadata and can be safely reprocessed. When a source document changes, older chunks are removed and replaced to avoid stale context being retrieved \parencite{KimothiAbhinav2025ASGt}. For internal PLM documents a special deletion approach is used, since Sovelia Core can maintain multiple versions of same document, but usually the latest released document contains the most up to date information. For this reason, the system automatically looks for old versions of the document to be updated and automatically deletes those keeping only the latest version. This ensures that the most recent information is always available to users. When deleting documents entirely from Sovelia Core, all versions are immediately removed. This is important from security aspect too: if a document is deleted due to sensitivity or confidentiality concerns, retaining its embeddings could lead to unauthorized access through the AI assistant for a document that should no longer be accessible.

\section{Retrieval mechanism}
\label{sec:retrieval-mechanism}

The retrieval mechanism connects user queries to relevant documentation. The implementation employs a tool-augmented hybrid RAG architecture that combines tool-based retrieval with re-ranking to balance retrieval quality, response time, and access control requirements.

\subsection{Tool-augmented (agentic) query processing}
\label{subsec:query-processing}

The system implements a tool-augmented, tool-calling architecture where the language model can use specialized tools rather than following a fixed retrieve-then-generate pipeline. This design builds upon the ReAct framework \parencite{yaoReActSynergizingReasoning2022}. The model can decide whether retrieval is necessary and can invoke retrieval multiple times with refined queries. This can be highly useful in PLM context, where questions can be highly domain specific and procedural which can require multiple searches of the document database.

In this thesis, the term \emph{agentic} is used in a narrow sense \parencite{plaatAgenticLargeLanguage2026}: the model can decide when to invoke read-only retrieval tools and how to interact with the user, but it does not independently execute high-impact actions in external systems. This differs from "fully-automatic" agentic implementations, where AI agents can e.g. interact in multi-agent or multi-modal environments.

When a user submits a query, the language model can invoke a documentation retrieval tool and then generate the response using the returned context. This enables selective retrieval and iterative refinement when initial results are insufficient \parencite{fengRetrievalGenerationSynergyAugmented2024}. As the queries can vary in complexity the language model can decide if it needs additional information, wants to rewrite user's query or continue searching for answers iteratively.

The retrieval tool (\texttt{plm\_documentation\_retriever}) accepts a natural language query and returns documentation snippets with source metadata, enabling citations even when multiple retrieval rounds are used.

\subsection{Retrieval quality, permissions, and provenance}
\label{subsec:hybrid-retrieval}

The retrieval tool implements hybrid retrieval by combining vector similarity search with BM25 re-ranking \parencite{robertsonProbabilisticRelevanceFramework2009}. Initial vector search retrieves a larger candidate set of 20 semantically similar articles, followed by BM25-based re-ranking and a weighted hybrid score (60\% for semantic similarity and 40\% for BM25) to produce the final result set of top-5 chunks. Similar approaches were investigated by \textcite{bruchAnalysisFusionFunctions2024} where hybrid retrieval was found to improve precision in in-domain search tasks.

\label{subsec:permission-filtering}
Permission filtering is applied during retrieval using database queries, so unauthorized chunks are not returned to the model. This supports both security and retrieval quality compared to post-filtering approaches \parencite{zhongHoneyBeeEfficientRolebased2025, jeongPermissionAwareRAGIdentity2025}.

\label{subsec:source-tracking}
Each retrieved chunk includes metadata about its source document. For internal PLM documents, this includes the unique document identifier, document revision, and description. For external documentation, this includes the article title and URL. Source metadata supports provenance in responses, enabling verification and navigation to the underlying documentation \parencite{NEURIPS2020_6b493230}.

\section{Prompt engineering and LLM integration}
\label{sec:prompt-engineering}

The prompt provides the model with tool access and instructions, so retrieval is performed selectively rather than unconditionally. This follows the tool-use pattern described in ReAct-style prompting \parencite{yaoReActSynergizingReasoning2022}. The system prompt defines the assistant role, available tools, and behavioral constraints, and it instructs the model to use the \texttt{plm\_documentation\_retriever} tool when documentation evidence is required \parencite{yaoReActSynergizingReasoning2022, NEURIPS2020_6b493230}.

The prompt also requires aims to handle uncertainty and source attribution to reduce hallucination risk and support transparency expectations \parencite{NEURIPS2020_6b493230, sillbergEUAIAct2025}. This is achieved by including explicit anti-hallucination instructions that apply both to parametric generation and tool-augmented generation. The model receives guidance to cite specific sources when information derives from retrieved documentation, to avoid fabricating links or references, and to acknowledge uncertainty when retrieved context does not contain sufficient information to answer a query.

\label{subsec:conversation-history}
Conversation history is retained to support multi-turn assistance, where follow-up questions can build on earlier context and earlier retrieval results. This done to support iterative information seeking behavior typical in AI assistants \parencite{petricekAIAssistantsFramework2023, budiu6TypesConversations2023}, where iterative interaction patterns enable users to refine queries and provide feedback through natural dialogue rather than single-shot requests

\label{subsec:model-configuration}
Model selection is configurable at runtime through the administration UI to support both cloud-based and on-premises deployment. Building on the provider abstraction layer (\autoref{subsec:provider-abstraction-layer}), this preserves data residency options and addresses sovereignty concerns raised for AI use in manufacturing and PLM environments \parencite{wangArtificialIntelligenceProduct2021}. Iterative retrieval is supported when initial results are insufficient \parencite{fengRetrievalGenerationSynergyAugmented2024}.

\section{API design and access control}
\label{sec:api-design}

The API layer provides secure access to AI functionality through RESTful endpoints integrated with Sovelia Core's existing authentication and authorization mechanisms.

The API exposes endpoints for submitting queries, retrieving conversation history, and storing feedback. Authentication is enforced through Sovelia Core session management. The validated user identifier flows through to retrieval to enable permission filtering. Errors are categorized as validation errors, permission errors, and service errors \parencite{coblenzQualitativeStudyREST2023}.

A dedicated testing endpoint enables administrators to validate system configuration without affecting production conversations. This endpoint accepts model configuration parameters and attempts to connect to the specified provider, returning success or failure with diagnostic information. This endpoint is connected to Sovelia Core's administration UI, allowing administrators to test model configurations before enabling them for end users.

\section{User interface integration}
\label{sec:user-interface-integration}

The AI assistant integrates directly into Sovelia Core's web interface as a contextual help panel, providing a chat interface with message history and input field. The design supports iterative, human-in-the-loop interaction typical for AI assistants \parencite{petricekAIAssistantsFramework2023, budiu6TypesConversations2023}. Figure~\ref{fig:sovelia-chat-ui} shows the chat interface implemented as a popup that can be opened or closed without disrupting the main PLM workflow.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{figures/sovelia-chat-ui.png}
  \caption{AI assistant chat interface integrated into Sovelia Core home screen (pre-release version)}
  \label{fig:sovelia-chat-ui}
\end{figure}

AI responses render Markdown for readability in technical content. Each response includes clickable source references that appear alongside AI responses as interactive elements. For internal PLM documents, clicking a source reference opens the document object in Sovelia Core. For external documentation, clicking a source reference opens the URL in a new browser tab. This integration enables seamless transition from AI-assisted discovery to detailed document review. Showing the sources directly in the UI addresses the transparency and verifiability requirements identified by \textcite{NEURIPS2020_6b493230}, where users must be able to trace AI-generated information back to authoritative documents to build trust and ensure accuracy in technical contexts. The prominence of source references also supports exploring conversations, as \parencite{budiu6TypesConversations2023} observed that users engaged in depth-focused learning benefit from explicit pathways to detailed documentation that can inform subsequent followup questions.

Each response includes per-message feedback controls (thumbs up / thumbs down). Feedback is stored for later analysis and continuous improvement \parencite{petricekAIAssistantsFramework2023, knollmeyerDocumentGraphRAGKnowledge2025}. Users can clear conversation history to reset context. Conversations are soft-deleted (flagged as deleted) rather than physically removed, supporting auditability and later analysis \parencite{budiu6TypesConversations2023}.

\section{Operational considerations}
\label{sec:operational-considerations}

Operational features support production deployment by providing logging, runtime configuration, and basic resource controls \parencite{KimothiAbhinav2025ASGt}.

For observability, the embedding service and application server maintain logs for document processing, query handling, and error conditions. Log rotation is used to manage storage growth \parencite{KimothiAbhinav2025ASGt}.

Runtime configuration is supported through the Sovelia Core administration UI, which is used to manage key parameters such as provider selection, API keys, and retrieval criteria.

Basic resource controls are implemented with queue-based processing for embedding generation and database connection pooling, aiming to keep the system responsive under load \parencite{KimothiAbhinav2025ASGt}.

\section{Design implications}
\label{sec:system-design-implications}

The implemented architecture indicates that a practical RAG assistant can be integrated into an on-premises PLM environment by prioritizing governance-aligned defaults over maximal model sophistication. In particular, enforcing access control during retrieval (instead of after generation) shifts confidentiality from a prompt-level expectation to a system-level guarantee, which is essential for PLM deployments where documents often include controlled product and process knowledge \parencite{jeongPermissionAwareRAGIdentity2025, zhongHoneyBeeEfficientRolebased2025}. Using PostgreSQL with pgvector further suggests that acceptable retrieval latency and maintainability can be achieved without introducing a separate vector database component, which reduces operational coupling and simplifies deployment in existing PLM infrastructures.

Several trade-offs remain explicit. Hybrid retrieval and tool-calling improve robustness and potentially user-perceived answer quality, but they add moving parts that must be operated (configuration, monitoring, and failure handling) in a production setting \parencite{KimothiAbhinav2025ASGt}. Likewise, the documentation pipeline reduces stale context through reprocessing and version control, yet it introduces dependency on reliable ingestion schedules and on consistent source metadata. These considerations imply that evaluation must address both \emph{response quality} and \emph{operational characteristics} rather than treating the assistant purely as a model output.

The next chapter therefore evaluates the assistant through (1) structured expert assessment of response accuracy, relevance, completeness, and source attribution, and (2) technical performance measurements that quantify latency, tool usage, and token consumption under realistic usage patterns. This evaluation focus reflects the thesis emphasis on implementable on-premises RAG patterns for enterprise PLM, where usefulness depends on both grounded answers and predictable operation.
