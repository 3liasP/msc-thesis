\chapter{Evaluation and results}
\label{ch:evaluation-and-results}

This chapter presents the evaluation of the RAG-based AI assistant integrated with Sovelia Core. The evaluation follows a dual approach combining expert analysis of system responses with technical performance measurements. This methodology aligns with the design science research framework outlined in Chapter~\ref{ch:research-methodology}, assessing both the artifact's utility (does it solve the identified problem?) and its technical performance (does it function as designed?). The evaluation examines response quality through systematic expert review and quantifies operational characteristics through performance metrics collected during testing deployment.

\section{Evaluation methodology}
\label{sec:evaluation-methodology}

The evaluation strategy employs two complementary methodologies: expert evaluation of RAG system responses and technical performance analysis. This dual approach addresses different dimensions of system quality, with expert evaluation focusing on response accuracy, relevance, and trustworthiness, while performance metrics quantify operational characteristics such as latency, throughput, and token consumption.

\subsection{Test environment and configuration}
\label{subsec:test-environment}

All evaluation activities were conducted on a development workstation running Ubuntu 22.04.5 LTS (Jammy Jellyfish) with an Intel Core i7-1360P processor (16 cores, 5.00 GHz maximum frequency), 32 GiB system memory, and 2 TiB storage capacity. The system utilized integrated Intel graphics (Intel Iris Xe Graphics) without dedicated GPU acceleration. The system operated the Sovelia Core RAG implementation with PostgreSQL database and pgvector extension for vector similarity search, representing a typical on-premise development environment suitable for testing and evaluation.

The RAG system configuration employed two key AI service components:

\begin{itemize}
    \item \textbf{Embedding model}: Nomic Embed Text (nomic-embed-text) via Ollama, running locally on the development workstation for generating 768-dimensional vector embeddings of both documentation chunks and user queries. This open-source embedding model provides efficient semantic representation suitable for on-premise deployment. The embedding model remained constant across all performance tests, running on the CPU-only development workstation in both configurations.

    \item \textbf{Language models}: To assess practical trade-offs between cloud-based proprietary and on-premise open-source LLM deployments, performance testing was conducted using two different providers:
          \begin{itemize}
              \item \textbf{OpenAI GPT-5 Nano} (gpt-5-nano) via OpenAI API, representing cloud-based proprietary model deployment with API costs but minimal local infrastructure requirements.
              \item \textbf{Ollama GPT-OSS-20B} (gpt-oss-20b) hosted on a remote Dell PowerEdge R760XA GPU server at Tampere University, representing on-premise open-source deployment. The server specification included 4$\times$ NVIDIA L40S GPUs (48 GB VRAM each, 192 GB total), 1 TB system memory, Intel Xeon Gold 6548Y+ processor (32 cores, 64 threads), dual 100 GbE network interfaces (Broadcom 57508), and 4.5 TB storage capacity. This configuration represents enterprise-grade GPU infrastructure suitable for production LLM inference.
          \end{itemize}
\end{itemize}

The vector database contained 113 documents processed into 217 chunks at the time of evaluation, comprising Sovelia Core help documentation from Document360, release notes from Umbraco, and sample customer standard operating procedure documents. The system was configured to retrieve three documentation sources per query by default, though this parameter is adjustable in the implementation.

This test environment represents a realistic on-premise deployment scenario where embedding generation occurs locally on application server hardware while LLM inference is offloaded either to cloud API services or dedicated GPU infrastructure. This hybrid architecture reflects deployment patterns common in organizations balancing data governance requirements, infrastructure investments, and performance objectives.

\subsection{Expert evaluation design}
\label{subsec:expert-evaluation-design}

Expert evaluation was conducted through structured analysis of RAG system responses to representative queries from the PLM documentation domain. This methodology draws on established practices in information retrieval evaluation \parencite{manningIntroductionInformationRetrieval2008a} and follows evaluation approaches used in domain-specific RAG systems \parencite{knollmeyerDocumentGraphRAGKnowledge2025,namLoRATunedMultimodalRAG2025}, adapted to the specific context of enterprise PLM documentation.

\subsubsection{Query set construction}

A balanced query set was constructed to represent the diversity of information needs encountered in Sovelia Core usage. The query set consists of 30 question pairs organized into five categories, each containing six questions, totaling 30 questions. The complete question set is provided in Appendix~\ref{app:evaluation-questions}. The five categories are:

\begin{enumerate}
    \item \textbf{Feature inquiries}: Questions about system capabilities, configuration options, and available features (e.g., ``What are the available lifecycle states for items in Sovelia Core?'', `` What types of reports are available in the Sovelia Core Template?'').

    \item \textbf{Procedural questions}: Step-by-step instructions for common tasks and workflows (e.g., `What is the process for creating a new item in Sovelia?'', ``How do I add components to a bill of materials structure?'').

    \item \textbf{Troubleshooting queries}: Questions about unexpected behavior and problem resolution (e.g., ``Why can't I check in my document after making changes?'', ``My search is taking too long and returning too many results. How can I cancel or refine it?'').

    \item \textbf{Version-specific questions}: Queries about features introduced in specific releases or changes between versions (e.g., ``What's new in Sovelia Core version 25.1?'', `` When was the drag and drop functionality introduced?'').

    \item \textbf{Integration questions}: Questions about CAD/ERP integration, data exchange, and cross-system workflows (e.g., ``How can I control which items are visible to external users through the Extranet?'', ``How does Sovelia Sync work with local file editing?'').
\end{enumerate}

The 30-question set size balances evaluation comprehensiveness with practical feasibility. This scale aligns with evaluation practices in domain-specific RAG implementations for technical documentation, where focused test sets allow for detailed qualitative assessment while maintaining feasibility \parencite{namLoRATunedMultimodalRAG2025}. Each category contains six questions to ensure sufficient representation of each query type while maintaining manageable evaluation workload. Example questions from each category are shown in Table~\ref{tab:example-questions}, with the complete set detailed in Appendix~\ref{app:evaluation-questions}.

Questions were formulated based on actual support inquiries, user documentation sections, and common onboarding challenges identified by Sovelia implementation consultants. This approach aims to ensure validity, meaning that the evaluation reflects real-world usage patterns rather than artificial test scenarios.

\subsubsection{Evaluation criteria}

The evaluation employs a factored assessment approach where responses are rated across multiple independent dimensions \parencite{abeysingheChallengesEvaluatingLLM2024}. This methodology addresses limitations of holistic evaluation approaches by decomposing response quality into specific measurable aspects, enabling more precise identification of system strengths and weaknesses. Each dimension is assessed independently using a 5-point Likert scale (1 = Very poor, 2 = Poor, 3 = Acceptable, 4 = Good, 5 = Excellent), providing granular quality measurements suitable for both quantitative aggregation and qualitative analysis.

The four evaluation dimensions are:

\begin{enumerate}
    \item \textbf{Factual accuracy}: Correctness of information provided in the response, verified against official Sovelia documentation and, where necessary, actual system behavior. This dimension assesses whether factual claims are accurate, whether technical details are correct, and whether procedures described align with documented workflows. Ratings range from very poor (contains substantial misinformation) through acceptable (mostly correct with minor inaccuracies) to excellent (fully accurate with precise technical details).

    \item \textbf{Relevance}: The degree to which the response addresses the user's specific information need as expressed in the query. This dimension evaluates whether the response directly answers the question asked, whether information provided aligns with the query's intent, and whether extraneous information is minimized. Ratings reflect how well the response matches the user's actual information need, from very poor (fails to address the question) to excellent (directly and comprehensively addresses the specific query).

    \item \textbf{Source attribution}: Quality and completeness of citations to source documentation. This dimension assesses whether sources are provided, whether cited sources are appropriate and authoritative, and whether sources actually support the claims made in the response. Strong source attribution enhances trustworthiness and enables users to verify information or explore topics in greater depth. Ratings range from very poor (no sources provided or sources do not support claims) to excellent (all major claims properly attributed to appropriate, verifiable sources).

    \item \textbf{Completeness}: Sufficiency of information provided to satisfy the user's information need without requiring follow-up queries. This dimension evaluates whether the response contains all information necessary to fully answer the question, whether important caveats or context are included, and whether the level of detail is appropriate for the query type. Ratings span from very poor (lacks critical information) to excellent (provides comprehensive information with appropriate detail and context).
\end{enumerate}

This multi-dimensional evaluation framework extends standard information retrieval metrics \parencite{manningIntroductionInformationRetrieval2008a} to address the specific challenges of RAG-based question answering in technical documentation contexts, where both retrieval quality and generation accuracy must be assessed \parencite{knollmeyerDocumentGraphRAGKnowledge2025}. The factored approach produces better insights into which specific aspects require improvement compared to holistic evaluation methods \parencite{abeysingheChallengesEvaluatingLLM2024}, making it particularly valuable for iterative system refinement. The framework recognizes that effective retrieval is fundamental to RAG performance, with recent work showing that query likelihood approaches can achieve competitive document ranking performance \parencite{zhuangOpensourceLargeLanguage2023}.

\subsubsection{Evaluation procedure}

The evaluation was conducted by domain experts with extensive knowledge of both Sovelia Core functionality and PLM workflows. These evaluators include the product owner of Sovelia Core and a senior implementation consultant with a combined experience of over 40 years in PLM systems. This expert panel approach mitigates individual bias while leveraging deep domain knowledge necessary to assess technical accuracy.

Responses evaluated were generated during the technical performance testing described in Section~\ref{sec:technical-performance-results}, where 30 queries were submitted to the RAG system under realistic load conditions using the test environment detailed in Section~\ref{subsec:test-environment}. This approach ensures that evaluated responses reflect actual system behavior under operational conditions rather than idealized single-query scenarios. Each query produced a generated answer with cited source documentation, which was captured along with performance metrics. The model used to generate responses for evaluation was the OpenAI GPT-5 Nano (gpt-5-nano) via OpenAI's API, representing a cloud-based proprietary LLM deployment.

The evaluation process employed a structured web-based form presenting each question alongside its generated response and cited sources. For each of the 30 question-answer pairs, evaluators assessed all four dimensions (factual accuracy, relevance, source attribution, completeness) using the 5-point Likert scale. The evaluation form also provided a free-text comment field for each question, enabling evaluators to document specific observations, identify particular strengths or weaknesses, and note examples of errors or exemplary responses.

The evaluation procedure for each question consisted of:

\begin{enumerate}
    \item \textbf{Response review}: Evaluators read the generated answer in full, assessing its structure, content, and presentation quality.

    \item \textbf{Factual verification}: Claims and technical details in the response were verified against official Sovelia documentation (Help articles and release notes). Where necessary, evaluators consulted the actual system behavior to confirm procedural instructions or feature descriptions.

    \item \textbf{Source examination}: The cited documentation sources provided with each response were examined to assess whether they were appropriate for the query and whether they actually supported the claims made in the generated answer.

    \item \textbf{Relevance assessment}: Evaluators judged whether the response directly addressed the user's information need as expressed in the question, noting any inclusion of irrelevant information or omission of pertinent details.

    \item \textbf{Completeness evaluation}: The sufficiency of the response was assessed, determining whether users would need to submit follow-up queries or consult additional documentation to fully address their information need.

    \item \textbf{Scoring and annotation}: Each dimension received a score from 1 (very poor) to 5 (excellent), accompanied by optional qualitative comments explaining the rationale for ratings, particularly for responses scoring below 4 or exhibiting notable characteristics.
\end{enumerate}

Evaluators completed the assessment independently, with subsequent discussion of divergent ratings to understand different perspectives and ensure consistent interpretation of evaluation criteria. The web-based form facilitated systematic data collection, with responses exported as structured JSON data for quantitative analysis.

\subsection{Technical performance metrics}
\label{subsec:technical-performance-metrics}

Technical performance evaluation quantifies operational characteristics of the RAG system under realistic load conditions using the test environment described in Section~\ref{subsec:test-environment}. These metrics provide insight into system scalability, resource requirements, and user experience quality from a performance perspective.

The implemented system employs an agentic architecture where the language model determines whether to invoke retrieval tools, execute multiple retrieval operations if necessary, and synthesize responses from gathered context. Performance measurement captures timing data across multiple pipeline stages:

\begin{enumerate}
    \item \textbf{Tool execution}: Total time spent executing agentic tools, primarily the documentation retrieval tool. The retrieval tool encompasses multiple sub-operations:
          \begin{itemize}
              \item \textbf{Query embedding}: Converting the user's query into a 768-dimensional vector representation using the locally-hosted Nomic Embed Text model via Ollama.
              \item \textbf{Vector search}: Retrieving the top-k most similar documentation chunks from PostgreSQL using pgvector's cosine similarity search. Recent research has demonstrated that open-source language models can effectively serve as zero-shot query likelihood models for document ranking \parencite{zhuangOpensourceLargeLanguage2023}, validating the effectiveness of similarity-based retrieval approaches.
              \item \textbf{BM25 reranking}: Applying BM25 lexical ranking to reorder vector search results based on term frequency and document statistics, improving precision for keyword-heavy queries.
              \item \textbf{Hybrid reranking}: Combining vector similarity scores with BM25 scores using weighted aggregation to balance semantic and lexical relevance signals.
              \item \textbf{Chunk grouping}: Organizing retrieved chunks by source document to provide coherent context boundaries for the language model.
          \end{itemize}

    \item \textbf{Embedding generation}: Time required to generate query embeddings for similarity search. This operation occurs within tool execution but is measured separately to isolate embedding model performance from retrieval logic.

    \item \textbf{LLM inference}: Time required for language model processing, which occurs in two distinct phases within the agentic architecture:
          \begin{itemize}
              \item \textbf{Tool decision phase}: The initial LLM call where the model determines whether to invoke retrieval tools, which specific tools to call, and with what parameters. This phase may result in zero, one, or multiple tool invocations depending on query complexity.
              \item \textbf{Response generation phase}: The final LLM call where the model synthesizes retrieved documentation context into a coherent response. The quality of generated responses depends critically on the model's ability to follow instructions and align with user intent \parencite{ouyangTrainingLanguageModels2022}, which has been enhanced through reinforcement learning from human feedback (RLHF) \parencite{kaufmannSurveyReinforcementLearning2024} in modern language models.
          \end{itemize}
\end{enumerate}

Performance data is captured through PostgreSQL stored procedures that measure elapsed time for each component and persist measurements to the \texttt{AIChatPerformance} table. Detailed metrics including tool call counts, LLM call counts, individual operation timings, and retrieval pipeline stage breakdowns are stored in a JSONB column for granular analysis. Total query latency represents the sum of all tool executions and LLM calls, providing an end-to-end user experience metric. Token usage statistics are extracted from LLM response metadata and logged to the \texttt{AIChatHistory} table, enabling cost analysis and context window utilization assessment.

For the documentation pipeline, performance metrics focus on:

\begin{enumerate}
    \item \textbf{Content extraction}: Time required to parse and extract text content from source documents (HTML from Document360 \parencite{Document360API} (Sovelia help \parencite{SoveliaHelp}) and Umbraco \parencite{UmbracoCMSDocumentation2025} (Sovelia release notes \parencite{ReleaseNewsAll}), structured content from Sovelia's internal format).

    \item \textbf{Chunk embedding}: Time required to generate vector embeddings for each documentation chunk using the local Nomic Embed Text model, representing the primary computational cost of the pipeline.

    \item \textbf{Processing throughput}: Documents and chunks processed per unit time, indicating the pipeline's ability to handle large documentation volumes during initial ingestion and periodic updates.
\end{enumerate}

These metrics provide quantitative insight into system performance characteristics, identifying potential bottlenecks and informing infrastructure sizing decisions for production deployments.

\section{Expert evaluation results}
\label{sec:expert-evaluation-results}

Expert evaluation of RAG system responses demonstrates strong overall performance across all four assessment dimensions, with mean scores ranging from 4,31 to 4,49 on the 5-point Likert scale (Table~\ref{tab:evaluation-summary}). This corresponds to quality ratings between ``Good'' and ``Excellent'' on average, indicating that the system produces responses of sufficient quality for operational use in PLM documentation support scenarios. All dimensions exhibited median scores of 5,0, revealing a positive skew in the distribution with most responses achieving the highest rating. Standard deviations between 1.01 and 1.15 indicate moderate variability, with most responses concentrated at high quality levels while a subset demonstrated room for improvement.

Source attribution achieved the highest mean score (4,49), reflecting the system's consistent provision of documentation references with generated responses. Factual accuracy (4,36) and completeness (4,32) received nearly identical ratings, suggesting that responses typically provide correct information with appropriate breadth and depth. Relevance scored marginally lower (4,31), indicating occasional instances where responses included extraneous information or did not fully align with the specific query intent. The narrow range between dimensions (0.18 points) demonstrates balanced performance, with no single dimension exhibiting substantial weakness relative to others.

\subsection{Variation across evaluators}
\label{subsec:evaluator-variation}

Analysis of evaluation scores by individual expert reveals notable consistency in rank ordering but systematic differences in absolute rating levels (Table~\ref{tab:evaluation-by-evaluator}). The product expert assigned the highest ratings across all dimensions (4,50--4,83), followed by the senior application engineer (4,40--4,63), with the product manager providing the most conservative assessments (3,80--4,07). This pattern persisted consistently, with the product manager scoring every dimension approximately 0,6--0,8 points lower than the product expert.

These evaluator differences likely reflect variation in assessment stringency rather than fundamental disagreement about response quality. The product manager's role emphasizes critical evaluation of customer-facing information and sensitivity to potential user confusion, possibly leading to more conservative quality assessments. The product expert's deep technical knowledge may enable recognition of subtle correctness that appears less evident to evaluators focused on practical usability. The product expert is also the one maintaining the Sovelia Help documentation \parencite{SoveliaHelp}, so they are most likely to be aware of the areas where the actual source information is lacking or incomplete. The senior application engineer's intermediate position and vast experience reflects balanced consideration of both technical accuracy and practical utility.

Despite absolute rating differences, evaluators demonstrated strong agreement on relative response quality, with problematic responses consistently receiving low scores from all evaluators and high-quality responses rated favorably across all the evaluators. This consistency in ranking validates the evaluation framework's ability to identify genuinely strong and weak responses independent of individual evaluator calibration.

\subsection{Performance by question category}
\label{subsec:category-performance}

RAG system performance varied substantially across the five question categories, revealing distinct patterns of strength and challenge (Table~\ref{tab:evaluation-by-category}). Version-specific questions achieved the highest mean scores (4,56--4,78), with particularly strong source attribution (4,78) reflecting the system's effectiveness at citing release notes. Procedural questions performed similarly well (4,39--4,72), indicating successful retrieval and synthesis of step-by-step instructions from help documentation. Arguably, Sovelia Help includes lots of step-by-step instructions for various central tasks, which makes it easier for the RAG system to find relevant information for procedural questions.

Integration questions exhibited the weakest performance (3,89--4,22), with relevance notably lower (3,89) than other dimensions. This pattern suggests challenges in addressing queries that span multiple system boundaries (CAD, PLM, ERP) where relevant information may be distributed across disparate documentation sources. The lower relevance scores indicate that responses occasionally included tangentially related information rather than precisely addressing the cross-system workflow aspects central to these queries. According to Product Expert, this area is also challenging because the documentation itself is lacking in this area, making it difficult for the RAG system to find relevant information. Additionally, in real customer scenarios, integration setups can vary significantly and are often customized, making it difficult to provide generic answers that fit all situations.

Feature inquiries and troubleshooting questions occupied intermediate positions (4,17--4,56), with troubleshooting showing slightly more balanced scores across dimensions while feature inquiries demonstrated particular strength in relevance (4,56). This pattern aligns with expectations, as feature documentation tends to be well-structured and comprehensively covered in help articles, while troubleshooting scenarios may require more nuanced interpretation of symptoms and context.

The category-level variation highlights areas for targeted improvement, particularly in handling integration scenarios where enhanced retrieval strategies or specialized prompt engineering may be warranted to better address multi-system workflows. Knowledge graphs or more structured documentation linking could also help improve performance in these complex query types by providing clearer context connections across documentation sources.

\subsection{Score distribution patterns}
\label{subsec:score-distribution}

The distribution of scores across the 5-point Likert scale reveals strong concentration at high quality levels, with 61--77\% of responses receiving the highest rating (Table~\ref{tab:evaluation-score-distribution}). Source attribution proved exceptionally strong, with 76.7\% of responses rated as excellent and only 7.8\% scoring below acceptable. Factual accuracy and completeness showed similar patterns, with approximately two-thirds of responses achieving excellent ratings and fewer than 10\% scoring in the poor or very poor range.

Relevance exhibited a somewhat broader distribution, with 61,1\% rated excellent but 20\% scoring at or below acceptable. This wider spread reflects the dimension's sensitivity to subtle mismatches between user intent and response content, where technically accurate information may nonetheless be presented with suboptimal focus or include tangential details. This could be potentially addressed through refined prompt engineering to better align response generation with user group needs.

The distribution tail reveals important limitations: 1,1--5,6\% of responses received the lowest rating across different dimensions, indicating rare but notable failure cases. These low-scoring responses occurred predominantly in integration questions and specific troubleshooting scenarios where the retrieval pipeline failed to locate appropriate documentation or where documentation gaps prevented adequate response generation.

The strong positive skew in score distributions validates the system's general reliability while highlighting that a small subset of queries (approximately 8--12\% scoring below 4,0) require attention. These problematic cases represent opportunities for targeted improvement through enhanced retrieval strategies, documentation coverage expansion, or query classification to identify scenarios requiring specialized handling.

\subsection{Detailed response quality patterns}
\label{subsec:detailed-patterns}

Question-level analysis reveals both exemplary performance and specific failure modes (Table~\ref{tab:evaluation-detailed}). Thirteen questions (43\% of the test set) achieved perfect or near-perfect scores (5,0 across all dimensions), demonstrating the system's capability to deliver excellent responses when documentation coverage and retrieval are effective. These high-performing questions span multiple categories, including version-specific queries (Q1.2--Q1.5), procedural instructions (Q2.2, Q2.5), troubleshooting scenarios (Q3.1, Q3.2), and integration questions (Q4.1, Q4.3, Q5.2).

Two questions exhibited substantial performance issues: Q3.5 (``My search is taking too long and returning too many results. How can I cancel or refine it?'') averaged 2,3--2,7 across dimensions, and Q4.2 (``Has the search functionality changed in the latest release?'') scored 2,3--2,7. These failures share common characteristics: both relate to user interface interactions (search refinement, functionality changes) where documentation coverage proves sparse or where relevant information exists in fragmented form across multiple sources. The low scores across all four dimensions indicate fundamental response inadequacy rather than isolated weaknesses in specific aspects.

Several questions demonstrated mixed performance with moderate scores (3,3--4,0), typically reflecting partial success where responses contained useful information but exhibited notable gaps or inaccuracies. For example, Q1.6 (``What user roles are available for managing product data in the Sovelia Template?'') averaged 3,3--3,7, suggesting that role-related documentation may be incompletely captured or that the retrieval pipeline struggled to locate comprehensive role definitions.

The detailed score patterns highlight that RAG system effectiveness depends critically on documentation coverage, with gaps or fragmentation in source material directly manifesting as response quality degradation. Questions where information exists in well-structured, comprehensive documentation consistently achieved high scores regardless of category, while queries addressing sparsely documented or highly distributed information struggled even when falling within otherwise strong categories.

\subsection{Qualitative insights from evaluator feedback}
\label{subsec:qualitative-insights}

Evaluator comments provide nuanced context for quantitative scores, revealing patterns of strength and weakness not fully captured by numerical ratings. Evaluators gave 41 detailed comments in total across 30 questions identifies five recurring themes: documentation coverage limitations, response structure and presentation quality, factual accuracy issues, version-specific information challenges, and effective multi-source synthesis. The comments were mainly critical, focusing on areas for improvement rather than praising strengths, which were often reflected in high scores without additional commentary.

\subsubsection{Documentation coverage as primary constraint}

The most frequently cited limitation related to gaps or incompleteness in source documentation rather than system deficiencies. Evaluators explicitly attributed response weaknesses to missing source material in multiple instances: ``this is only due to the fact that the documentation does not include this information'' (Q1.5, file format support), ``Most likely due to limited documentation'' (Q2.6, reporting improvements), and ``they are surely not mentioned in the documentation'' (Q3.6, troubleshooting reasons). This pattern appeared across question categories, with procedural questions suffering from incomplete step documentation and feature inquiries hampered by superficial coverage of configuration options.

Specific gaps identified included missing lists or enumerations where evaluators expected comprehensive coverage. For Q1.1 (lifecycle states), an evaluator noted that while ``the answer is pointing to the correct direction to find the information, a summary of states or example lifecycle states would have been useful.'' Similarly, Q1.5 (file format support) and Q1.3 (report descriptions) lacked specific enumerations that evaluators expected, with comments indicating these details were absent from source documentation. The RAG system proved unable to synthesize or infer missing information, instead providing directional guidance to relevant documentation sections without the specific details users sought.

Version-specific documentation presented particular challenges. One evaluator noted disappointment that the system ``doesn't access the internal release notes that get shipped with the product'' (Q4.1), highlighting a source coverage limitation where relevant information existed but remained outside the RAG system's retrieval scope. This structural limitation prevented comprehensive answers to version-comparison questions even when the underlying information existed within the organization.

\subsubsection{Response presentation and structure}

Beyond factual correctness, evaluators assessed response organization and clarity. Several comments identified presentation issues independent of content accuracy: ``Structure/presentation a bit off'' (Q4.1), ``Presentation looks a bit off'' (Q4.4), and ``feels like a mix up of different documents'' (Q2.2). These critiques suggest that even when accurate information was retrieved, the language model occasionally struggled to organize content coherently, particularly when synthesizing across multiple source documents.

Evaluators distinguished between technically complete responses and those optimized for user comprehension. For Q1.4 (product documents vs. general documents), one evaluator desired ``a bit more general/summarized answer,'' indicating that the response provided accurate procedural details but lacked an overview that would orient users before diving into steps. This pattern reveals tension between completeness and accessibility, where exhaustive accuracy may compromise practical usability. The Q5.1 comment (``True, in a way, but confusing way of saying it'') illustrates how technically correct responses can nonetheless impair understanding through awkward phrasing or overly complex explanations. Such cases suggest that factual accuracy scores may overestimate response utility when presentation quality degrades comprehension.

\subsubsection{Factual errors and hallucinations}

While rare, evaluators identified specific factual inaccuracies that undermined response trustworthiness. Q2.3 (adding BOM components) elicited concerns about hallucination, with one evaluator noting the response ``Somehow picked up the irrelevant Equipment BOM and confuses the answer with this'' and another asking ``Hallucination?'' This error demonstrates retrieval pipeline failures where semantically similar but contextually inappropriate content was retrieved and incorporated into responses.

Other factual errors included incorrect procedural requirements (Q2.1: ``Does not require ECO'') and wrong feature descriptions (Q1.1: ``Last status is wrong''). Q5.4 prompted skepticism about claimed functionality: ``In-production updates: Special update functions exist to modify these attributes for users with the right roles. --> I think not?'' These errors appeared to stem from misinterpretation of source documentation or conflation of related but distinct features, rather than complete fabrication.

Version-specific inaccuracies revealed temporal challenges in documentation management. Q4.2 (search functionality changes) suffered from the system finding ``an older version and claimed it as the latest version'' when no changes occurred in version 25.1. Similarly, Q4.5 (commenting feature introduction) missed that the feature was ``originally introduced at 22.2 version,'' suggesting retrieval pipeline difficulty in distinguishing feature introduction from subsequent enhancements or mentions.

\subsubsection{Incomplete procedural coverage}

Evaluators identified responses that provided partial but incomplete procedural guidance. Q2.3 noted ``nothing mentioned about the drag and drop method,'' indicating the response described one workflow while omitting an alternative approach. Q2.6 criticism that the answer ``doesn't introduce report generator that much'' and Q2.4 observation that ``It missed the 'normal' clone tool, introduced only the clone structure tool'' demonstrate a pattern where responses accurately described specific methods but failed to acknowledge alternative workflows or related functionality.

This incompleteness pattern suggests retrieval pipeline limitations in surfacing related procedural variations when initial retrieval focused on the most semantically similar content. Users seeking comprehensive understanding of available approaches would receive accurate but incomplete guidance, potentially missing simpler or more appropriate methods for their specific context. In some cases, the documentation itself may not have provided exhaustive procedural coverage, compounding the issue.

\subsubsection{Successful multi-source synthesis}

Despite identified weaknesses, evaluators recognized successful complex retrieval scenarios. Q4.6 received positive commentary: ``Used multiple resources to gather the information,'' indicating effective aggregation across documentation sources. Q3.3 elicited unqualified praise (``Great answer''), and Q4.1 acknowledgment that despite source limitations, ``from all the external sources available I think it did a good job.''

These positive cases demonstrate that when comprehensive, well-structured documentation exists and retrieval successfully identifies relevant chunks, the language model effectively synthesizes coherent responses. The evaluation reveals that system performance variability stems primarily from documentation characteristics and retrieval effectiveness rather than consistent generation quality issues.

The qualitative analysis reinforces that RAG system utility depends critically on source documentation quality and coverage. The system reliably transforms available documentation into responsive answers but cannot compensate for missing, outdated, or fragmented source material. This finding has direct implications for deployment strategy: successful RAG implementation requires concurrent investment in documentation quality improvement, not merely deployment of retrieval and generation infrastructure. Overall, the general consensus from quantitative scores and qualitative feedback given by evaluators indicates that the RAG system represents a valuable tool for enhancing PLM documentation accessibility, provided that source material is sufficiently comprehensive and well-maintained.

\section{Technical performance results}
\label{sec:technical-performance-results}

Performance evaluation was conducted using the 30-question evaluation set described in Section~\ref{subsec:expert-evaluation-design} on the test environment detailed in Section~\ref{subsec:test-environment}. To assess the practical trade-offs between local open-source and cloud-based proprietary language models, performance testing was conducted using two different LLM providers: OpenAI's GPT-5 Nano (gpt-5-nano) via API and Ollama's GPT-OSS-20B (gpt-oss-20b) running locally. These LLMs were selected, since they are relatively comparable across intelligence, price, speed, and context window size \parencite{artificialanalysisGPT5NanoHigh}, but represent proprietary cloud-based and open-source on-premise deployment models respectively. Both configurations utilized the same local Nomic Embed Text model for query and document embeddings, ensuring that observed differences reflect LLM provider characteristics rather than embedding model variations. The test environment consisted of simulated concurrent load with queries executed in a realistic usage pattern. Performance data was collected through PostgreSQL stored procedures and logged to dedicated performance tables. All the numbers shown in this section are rounded to one decimal place for improved readability. Complete numerical results with more decimal places and millisecond accuracy are provided in Appendix~\ref{app:performance-tables}.

\subsection{Overall latency characteristics}
\label{subsec:latency-characteristics}

Query latency measurements reveal substantial performance differences between cloud-based and on-premise GPU-accelerated LLM deployments (Table~\ref{tab:latency-distribution}). The OpenAI configuration achieved a mean total latency of 25,9 seconds with a median of 22,8 seconds and 95th percentile of 40,2 seconds. In contrast, the Ollama deployment on dedicated GPU infrastructure exhibited a mean latency of 91,4 seconds with median of 92,4 seconds and 95th percentile of 163,7 seconds. This represents approximately a 3,5$\times$ difference in end-to-end query response time, with the on-premise deployment consistently slower across all percentiles despite access to enterprise-grade GPU resources.

The latency distribution demonstrates relatively stable performance for the OpenAI configuration, with the 95th percentile remaining under 41 seconds. The Ollama configuration shows greater variability, with the 95th percentile approaching 2,7 minutes. This performance difference persists despite access to substantial GPU infrastructure (4$\times$ NVIDIA L40S GPUs, 192 GB VRAM total), though Ollama's architecture utilizes only a single GPU at a time rather than distributing inference across multiple devices. Potential contributing factors include this single-GPU limitation, model architecture efficiency differences between GPT-5 Nano and GPT-OSS-20B, network latency between the application server and remote GPU infrastructure, and optimizations in OpenAI's inference serving infrastructure. More sophisticated inference engines such as vLLM offer better multi-GPU parallelization and optimization strategies that could substantially improve on-premise deployment performance beyond what Ollama's architecture permits. Use of vLLM could be more appropriate for production deployments requiring lower latency and higher throughput across multiple concurrent users. \parencite{umeshOllamaVsVLLM2025}

Both configurations exhibited similar agentic behavior patterns, with average tool call counts of 1,30 (Ollama) and 1,33 (OpenAI) and average LLM call counts of 2,30 for both providers. This consistency indicates that the observed latency differences reflect computational performance characteristics rather than differences in reasoning behavior or retrieval strategy between the two models.

\subsection{Pipeline stage contribution}
\label{subsec:pipeline-stage-contribution}

Analysis of latency distribution across pipeline stages reveals that LLM inference dominates total query time for both configurations (Table~\ref{tab:stage-contribution}). The OpenAI configuration allocated 99,54\% of total latency to LLM processing, with query embedding consuming 0,36\% and tool execution (including retrieval) accounting for 0,41\% of total time. The Ollama configuration showed an even more pronounced concentration with 99,87\% attributed to LLM processing, with embedding generation and tool execution each contributing less than 0,1\%.

The absolute times for embedding generation and tool execution proved comparable between providers. Query embedding generation averaged 61 milliseconds for Ollama and 80 milliseconds for OpenAI, demonstrating that both configurations achieved similar performance for this CPU-bound operation on the local development workstation. Tool execution time (which includes embedding generation within the retrieval tool) averaged 79 milliseconds for Ollama versus 93 milliseconds for OpenAI, further confirming that retrieval pipeline operations perform consistently regardless of LLM provider selection.

This stage contribution analysis confirms that LLM inference optimization represents the primary opportunity for latency reduction, as retrieval and embedding operations contribute negligibly to total query time. The 3,5$\times$ performance difference between providers manifests almost entirely in the LLM processing stage.

\subsection{Retrieval pipeline performance}
\label{subsec:retrieval-pipeline-performance}

Detailed analysis of the retrieval pipeline reveals that all components perform efficiently and comparably across provider configurations (Table~\ref{tab:retrieval-stages}). Vector search using pgvector's cosine similarity averaged 15,71 milliseconds for Ollama queries and 11,65 milliseconds for OpenAI queries, demonstrating that database-level retrieval operations remain fast even under concurrent load. BM25 reranking added approximately 1,2 milliseconds (Ollama) and 0,9 milliseconds (OpenAI), while hybrid reranking and chunk grouping operations each contributed less than 0,1 milliseconds.

Total retriever time proved nearly identical between providers, averaging 78 milliseconds for Ollama and 92 milliseconds for OpenAI. This consistency confirms that the retrieval pipeline, including query embedding generation, vector search, reranking, and chunk grouping, performs independently of LLM provider selection. The comparable performance validates the architecture's separation of concerns, where retrieval operations on the application server remain unaffected by downstream LLM inference location.

These results demonstrate that the pgvector extension provides adequate performance for the tested scale (217 chunks across 113 documents), with the complete retrieval pipeline completing in under 100 milliseconds consistently. Database-level operations and embedding generation on CPU-only hardware prove sufficient for responsive retrieval, indicating that optimization efforts should focus on LLM inference latency rather than retrieval pipeline components.

\subsection{Agentic behavior and multi-step reasoning}
\label{subsec:agentic-behavior}

The agentic tool-calling architecture implemented in the RAG system exhibited measured multi-step reasoning behavior, though single-tool queries predominated in practice (Table~\ref{tab:tool-patterns}). The Ollama configuration produced multi-tool queries (where the LLM invoked the documentation retrieval tool multiple times before responding) in 23,33\% of cases, while the OpenAI configuration exhibited this behavior in 13,33\% of cases. Maximum tool calls reached 4 for Ollama and 6 for OpenAI within the test set, indicating that models occasionally determined that multiple retrieval operations were necessary to adequately address complex queries.

LLM call patterns reveal the two-phase structure of the agentic architecture (Table~\ref{tab:llm-patterns}). The first LLM call (tool decision phase) averaged 37,0 seconds for Ollama and 5,1 seconds for OpenAI, during which the model determines whether to invoke retrieval tools or respond directly. The second LLM call (response generation phase) averaged 42,2 seconds for Ollama and 16,4 seconds for OpenAI, where the model synthesizes retrieved context into the final response. The second-to-first call ratio of 4,85 for Ollama and 3,57 for OpenAI indicates that response generation consistently requires more computational effort than tool decision-making, likely reflecting the greater complexity of context synthesis compared to function calling decisions. The substantial latency difference between providers persists across both phases despite Ollama's access to dedicated GPU infrastructure, suggesting that model architecture efficiency and inference optimization contribute more significantly to response time than raw computational capacity.

The relatively low incidence of multi-tool behavior (13-23\% of queries) suggests that most queries in the evaluation set could be adequately addressed with a single retrieval operation. This pattern may reflect either the focused nature of the test queries or the model's conservative approach to tool invocation, preferring to generate responses from initially retrieved context rather than iteratively refining retrieval.

\subsection{Token consumption and operational costs}
\label{subsec:token-costs}

Token usage analysis for the OpenAI configuration (Table~\ref{tab:token-cost-summary}) reveals moderate consumption patterns across the 30-query evaluation set. Input tokens totaled 97 471 (averaging 3 249 tokens per query), reflecting the combined size of system prompts, retrieved documentation context, and user queries. Output tokens totaled 53 769 (averaging 1 792 tokens per response), indicating that generated responses were substantive and detailed.

At GPT-5 Nano pricing of \$0,05 per million input tokens and \$0.40 per million output tokens, the total cost for the 30-query evaluation amounted to \$0,03 (\$0,00 for input, \$0,02 for output). This translates to approximately \$0,001 per query, suggesting that API costs for production deployment would remain negligible for typical usage volumes in Sovelia Core's target deployment scenarios. In a enterprise deployment with 1,000 queries per day, monthly costs would approximate \$30 (\$0,001 \times 1000 \times 30 = \$30), which is likely justifiable given the performance benefits observed. However, cost considerations must be balanced against performance requirements, data governance policies, and infrastructure investments.

The Ollama on-premise deployment incurs no per-query API costs, though it requires substantial GPU infrastructure investments (enterprise GPU servers, networking, maintenance). The observed 3,5$\times$ latency difference between providers despite dedicated GPU infrastructure suggests that cost-performance trade-offs extend beyond simple API cost comparisons to include infrastructure amortization, operational complexity, and performance requirements. Organizations with existing GPU infrastructure, strict data residency requirements, or very high query volumes may find on-premise deployment economically viable despite performance limitations, while those prioritizing responsiveness and minimizing infrastructure complexity may justify API costs for cloud-based models.

\subsection{Performance implications for deployment}
\label{subsec:performance-implications}

The performance evaluation results reveal several critical implications for RAG system deployment in on-premise PLM environments:

\textbf{LLM provider selection} emerges as the dominant factor in query latency, with cloud-based proprietary models (OpenAI GPT-5 Nano) delivering approximately 3,5$\times$ faster responses than on-premise open-source alternatives (Ollama GPT-OSS-20B) despite the latter's access to enterprise-grade GPU infrastructure (4$\times$ NVIDIA L40S, 192 GB VRAM total). This performance differential reflects multiple factors: Ollama's architectural limitation to single-GPU utilization (preventing multi-GPU parallelization), model architecture efficiency differences, inference optimization disparities, and network latency between application server and remote GPU infrastructure. More sophisticated inference engines such as vLLM provide better multi-GPU parallelization and optimization strategies that could substantially narrow this performance gap for on-premise deployments. \parencite{umeshOllamaVsVLLM2025} Organizations must balance performance considerations against data governance requirements, API costs, infrastructure investments, and dependency on external services. The 26-second mean response time for the cloud configuration approaches acceptable interactive thresholds, while the 91-second on-premise deployment time might exceed user patience for real-time assistance.

\textbf{Infrastructure requirements} differ substantially between deployment models. On-premise LLM deployment requires dedicated GPU infrastructure to achieve viable inference performance, though the tested Ollama configuration demonstrates that substantial GPU resources (192 GB VRAM across 4 GPUs, enterprise-grade compute) remain underutilized due to single-GPU architectural constraints. Alternative inference frameworks optimized for multi-GPU deployments could better leverage available hardware resources and approach cloud-optimized model performance. The cloud-based approach requires only sufficient capacity for embedding generation and vector search on the application server, both of which perform adequately on standard server hardware, while offloading computationally intensive LLM inference to optimized cloud infrastructure.

\textbf{Retrieval pipeline efficiency} demonstrates that vector database operations remain performant at the tested scale, with similarity search completing in under 20 milliseconds consistently. This finding suggests that pgvector provides adequate performance for Sovelia Core's documentation scale (hundreds of documents, thousands of chunks) without requiring specialized vector database infrastructure. Embedding generation on CPU-only application server hardware represents a potential optimization opportunity, with GPU acceleration likely reducing this component of latency.

\textbf{Agentic architecture overhead} proves minimal, with multi-step reasoning rarely triggered (13-22\% of queries) and tool decision latency remaining a small fraction of total query time. This pattern validates the agentic design choice, as the flexibility to perform multiple retrievals when necessary does not significantly impact typical single-retrieval query performance.

\textbf{Cost-performance trade-offs} favor cloud-based deployment for interactive assistance use cases, where sub-30-second response times justify minimal per-query costs (\$0.001). Local deployment may remain appropriate for batch processing scenarios, offline environments, or organizations with strict data residency requirements, provided that infrastructure investments can reduce inference latency through GPU acceleration.

These findings inform deployment recommendations for organizations implementing RAG-based documentation assistance in on-premise PLM systems, highlighting the tension between performance, cost, and data governance that characterizes enterprise AI deployment decisions.

\section{Discussion of findings}
\label{sec:discussion-of-findings}

The evaluation results demonstrate that RAG-based documentation assistance can achieve operationally viable quality in on-premise PLM environments, though success depends critically on source documentation coverage and LLM provider selection. This section interprets the evaluation findings and discusses implications for RAG system design in PLM contexts. Study limitations and future research directions are addressed in Chapter~\ref{ch:conclusion}.

\subsection{Interpretation of evaluation results}

The expert evaluation results (mean scores 4,31--4,49) indicate that the RAG system produces responses of sufficient quality for operational deployment in PLM documentation support scenarios. This performance level, corresponding to ratings between ``Good'' and ``Excellent,'' suggests that the system can meaningfully reduce documentation search time and improve information accessibility for Sovelia Core users. The high median scores (5,0 across all dimensions) reveal that most responses meet user needs effectively, though the moderate standard deviations (1,01--1,15) highlight a subset of queries requiring improvement.

The relatively narrow range between evaluation dimensions (0,18 points) demonstrates balanced system performance, with no single aspect exhibiting substantial weakness. Source attribution achieved the highest scores (4,49), validating the design decision to provide documentation references alongside generated responses. This transparency enhances trustworthiness and enables users to verify information or explore topics in greater depth, addressing a key concern in enterprise AI deployment where accountability and auditability are essential.

The substantial variation in performance across question categories reveals important patterns. Version-specific questions (4,56--4,78) and procedural questions (4,39--4,72) performed well, reflecting effective retrieval and synthesis from structured help documentation and release notes. Integration questions exhibited notably weaker performance (3,89--4,22), particularly in relevance (3,89), indicating challenges in addressing queries spanning multiple system boundaries (CAD, PLM, ERP). This pattern suggests that current documentation structure may not adequately support cross-system workflow questions, a finding with direct implications for documentation improvement priorities.

Qualitative feedback from evaluators consistently identified documentation coverage as the primary constraint on response quality rather than retrieval or generation failures. Evaluators explicitly attributed response weaknesses to missing source material in multiple cases, noting that ``the documentation does not include this information'' or ``they are surely not mentioned in the documentation.'' This pattern indicates that the RAG system reliably transforms available documentation into responsive answers but cannot compensate for gaps, incompleteness, or fragmentation in source material. The system's limitations reflect documentation limitations, not fundamental technical inadequacies in the RAG architecture.

Performance evaluation reveals substantial differences between the tested deployment configurations. The cloud-based OpenAI configuration achieved 25,9-second mean latency compared to 91,4 seconds for the Ollama deployment running on dedicated GPU infrastructure. This performance gap persists despite access to enterprise-grade GPU resources (4$\times$ NVIDIA L40S, 192 GB VRAM total), primarily reflecting Ollama's architectural limitation to single-GPU utilization, differences between the specific models tested (GPT-5 Nano versus GPT-OSS-20B), and inference optimization disparities between OpenAI's production infrastructure and the Ollama framework. More sophisticated inference frameworks such as vLLM with multi-GPU parallelization could substantially narrow this gap for on-premise deployments, suggesting that the observed performance difference reflects configuration and optimization choices rather than fundamental on-premise limitations. The minimal token costs (\$0,001 per query, approximately \$30 monthly for 1 000 queries daily) demonstrate that API expenses remain economically justifiable for interactive assistance scenarios where sub-30-second response times enhance user experience, though optimized on-premise deployments may achieve competitive performance with appropriate framework selection.

The finding that LLM inference dominates total latency (99,5\%+) while retrieval operations complete in under 100 milliseconds has important architectural implications. Optimization efforts should focus on LLM selection and deployment configuration rather than vector database or embedding model improvements. The pgvector extension provides adequate performance at the tested scale (217 chunks, 113 documents), indicating that specialized vector database infrastructure offers minimal benefit for documentation collections of this magnitude.

\subsection{Implications for RAG system design in PLM contexts}

The evaluation findings yield several design principles for RAG-based documentation assistance in on-premise PLM environments:

\textbf{Documentation quality drives system effectiveness.} The consistent pattern of documentation gaps limiting response quality demonstrates that RAG deployment requires concurrent investment in source material improvement. Organizations cannot compensate for incomplete or fragmented documentation through more sophisticated retrieval algorithms or larger language models. Successful deployment necessitates documentation audits identifying coverage gaps, particularly in integration scenarios, troubleshooting procedures, and configuration options. The finding that 43\% of queries achieved perfect or near-perfect scores while 8--12\% scored below acceptable quality (4,0) suggests that targeted documentation improvement in weak areas could substantially elevate overall system performance.

\textbf{Hybrid cloud-local architectures offer practical deployment paths.} The tested configuration, where embedding generation occurs locally while LLM inference utilizes cloud APIs, demonstrates a viable middle ground between complete on-premise deployment and full cloud migration. This approach addresses data governance concerns (documentation remains on-premise during retrieval) while leveraging cloud infrastructure for computationally intensive generation tasks. Organizations with strict data residency requirements could implement document-level access controls ensuring that only non-sensitive content reaches cloud LLMs, or deploy local LLMs with performance trade-offs for sensitive query scenarios. The minimal API costs (\$0,001 per query) make cloud-based generation economically viable even for organizations with existing GPU infrastructure, particularly when interactive responsiveness is prioritized.

\textbf{Retrieval pipeline simplicity proves sufficient.} The evaluation demonstrates that straightforward vector similarity search with BM25 reranking performs adequately for PLM documentation scenarios, completing in under 100 milliseconds consistently. More complex retrieval strategies such as query expansion, multi-stage reranking, or knowledge graph augmentation may offer marginal improvements but add implementation complexity without addressing the fundamental constraint of documentation coverage. At the tested scale, pgvector provides adequate performance without requiring specialized vector database infrastructure. This finding suggests that organizations can implement effective RAG systems using familiar PostgreSQL infrastructure rather than adopting additional database technologies.

\textbf{LLM provider selection dominates performance characteristics.} The approximately 3,5$\times$ latency difference between cloud-based and on-premise deployments, despite substantial GPU infrastructure access, demonstrates that LLM inference optimization represents the primary opportunity for performance improvement. Organizations must balance performance considerations against data governance requirements, API costs, infrastructure investments, and dependency on external services when selecting deployment models. The 26-second mean response time for the cloud configuration approaches acceptable interactive thresholds, while the 91-second on-premise deployment time may exceed user patience for real-time assistance scenarios.

These design principles inform deployment decisions for organizations implementing RAG-based documentation assistance in comparable on-premise PLM environments, highlighting the critical interdependencies between documentation quality, architectural choices, and performance requirements that shape system effectiveness.
