\chapter{Evaluation and results}
\label{ch:evaluation-and-results}

This chapter presents the evaluation of the RAG-based AI assistant integrated with Sovelia Core. The evaluation follows a dual approach combining expert analysis of system responses with technical performance measurements. This methodology aligns with the design science research framework outlined in Chapter~\ref{ch:research-methodology}, assessing both the artifact's utility (\textit{does it solve the identified problem?}) and its technical performance (\textit{does it function as designed?}). The evaluation examines response quality through systematic expert review and quantifies operational characteristics through performance metrics collected during testing deployment.

\section{Evaluation methodology}
\label{sec:evaluation-methodology}

The evaluation strategy employs two complementary methodologies: expert evaluation of RAG system responses and technical performance analysis. This dual approach addresses different dimensions of system quality, with expert evaluation focusing on response accuracy, relevance, and trustworthiness, while performance metrics quantify operational characteristics such as latency, throughput, and token consumption.

\subsection{Test environment and configuration}
\label{subsec:test-environment}

All evaluation activities were conducted on a development workstation running Ubuntu 22.04.5 LTS (Jammy Jellyfish) with an Intel Core i7-1360P processor (16 cores, 5.00 GHz maximum frequency), 32 GiB system memory, and 2 TiB storage capacity. The system utilized integrated Intel graphics (Intel Iris Xe Graphics) without dedicated GPU acceleration. A Sovelia Core install with the RAG implementation ran on the system with PostgreSQL database and pgvector extension for vector similarity search, which represents a fairly typical on-premise development environment suitable for testing and evaluation.

The RAG system configuration employed a single embedding model and two alternative language model deployments. Nomic Embed Text via Ollama was used to generate 768-dimensional vector embeddings for both documentation chunks and user queries. This embedding configuration remained constant across all tests and was executed locally on the CPU-only workstation.

To compare cloud-based proprietary and on-premise open-source LLM deployments, performance testing was conducted using OpenAI GPT-5 Nano via the OpenAI API and Ollama GPT-OSS-20B hosted on a remote Dell PowerEdge R760XA GPU server at Tampere University. The remote server specification included 4$\times$ NVIDIA L40S GPUs (48 GB VRAM each), 1~TB system memory, an Intel Xeon Gold 6548Y+ processor (32 cores, 64 threads), and dual 100~GbE network interfaces.

The vector database contained 113 documents processed into 217 chunks at the time of evaluation, comprising Sovelia Core help documentation from Document360, release notes from Umbraco, and a set of sample customer standard operating procedure documents. The system was configured to retrieve five documentation sources per query by default, though this parameter is adjustable in the configuration options.

Overall this test environment represents a realistic on-premise deployment scenario where embedding generation occurs locally on application server hardware while LLM inference is offloaded either to cloud API services or dedicated GPU infrastructure. Because no actual deployments of Sovelia Core with AI features exist, this hybrid architecture reflects an estimation of practical deployment models for enterprise RAG systems, striking a balance between local control of sensitive data and leveraging powerful cloud-based LLM capabilities.

\subsection{Expert evaluation design}
\label{subsec:expert-evaluation-design}

Expert evaluation was conducted through structured analysis of RAG system responses to representative queries from the PLM documentation domain. This methodology draws on established practices in information retrieval evaluation \parencite{manningIntroductionInformationRetrieval2008a} and follows evaluation approaches used in domain-specific RAG systems \parencite{shejutiExtendedAbstractEnhancing2025, namLoRATunedMultimodalRAG2025}, adapted to the specific context of enterprise PLM documentation.

This evaluation design is close to Nam et al.'s mixed-method approach, where automatic response quality indicators were complemented with structured Likert-scale assessment by domain users and qualitative feedback \parencite{namLoRATunedMultimodalRAG2025}. In this thesis, the emphasis is placed on expert judgment of correctness and source support, because enterprise documentation assistants are primarily required to provide verifiable, source-grounded guidance rather than answers that merely resemble a reference response.

\subsubsection{Query set construction}

A balanced query set was constructed to represent the diversity of information needs encountered in Sovelia Core usage. The query set consists of 30 questions organized into five categories (six questions per category): feature inquiries, procedural questions, troubleshooting queries, version-specific questions, and integration questions. The complete question set is provided in Appendix~\ref{app:evaluation-questions}, and examples are shown in Table~\ref{tab:example-questions}.

The 30-question set size aims to balance evaluation comprehensiveness with practical feasibility. This scale aligns with evaluation practices in domain-specific RAG implementations for technical documentation, where focused test sets allow for detailed qualitative assessment while maintaining feasibility \parencite{namLoRATunedMultimodalRAG2025}. Each category contains six questions to ensure sufficient representation of each query type while maintaining manageable evaluation workload.

Questions were formulated based on actual support inquiries, user documentation sections, and common onboarding challenges identified by Sovelia implementation consultants, but also based on experience of the author as a Sovelia Core developer and thus intimate knowledge of typical user needs. This approach aims to ensure validity, meaning that the evaluation reflects real-world usage patterns rather than artificial test scenarios. Most of the questions have specific answers in the documentation, while a few are more open-ended to reflect realistic information-seeking behavior. Some of questions are also designed to be more challenging, for example by requiring synthesis across multiple documents or by addressing areas where documentation coverage is known to be limited. This mix of question types allows for a nuanced assessment of system capabilities across different information retrieval challenges.

\subsubsection{Evaluation criteria}

The evaluation employs a factored assessment approach where responses are rated across multiple independent dimensions \parencite{AbeysingheBhashithe2024TCoE}. Each dimension is assessed independently using a 5-point Likert scale (1 = Very poor, 2 = Poor, 3 = Acceptable, 4 = Good, 5 = Excellent).

Four dimensions were assessed. \textit{Factual accuracy} measures correctness of claims against official Sovelia documentation (and, when needed, observed system behavior). \textit{Relevance} measures how directly the response addresses the query without unnecessary content. \textit{Source attribution} measures whether citations are provided and whether cited sources support the stated claims. \textit{Completeness} measures whether the response provides sufficient information to satisfy the query without requiring follow-up questions or additional research.

The use of a 5-point Likert instrument mirrors prior domain evaluations where multiple user-facing dimensions were rated (e.g., response speed, clarity, usability, and perceived reliability) \parencite{namLoRATunedMultimodalRAG2025}. However, the dimensions differ intentionally: for a documentation assistant in a PLM context, traceability to retrieved sources is treated as a first-class requirement, and source attribution is therefore assessed explicitly.

This multi-dimensional evaluation framework extends standard information retrieval metrics \parencite{manningIntroductionInformationRetrieval2008a} to address the specific challenges of RAG-based question answering in technical documentation contexts, where both retrieval quality and generation accuracy must be assessed \parencite{namLoRATunedMultimodalRAG2025}. The factored approach produces better insights into which specific aspects require improvement compared to holistic evaluation methods \parencite{AbeysingheBhashithe2024TCoE}, making it particularly valuable for iterative system refinement. The framework recognizes that effective retrieval is fundamental to RAG performance, with recent work showing that query likelihood approaches can achieve competitive document ranking performance \parencite{ZhuangShengyao2023OLLM}.

\subsubsection{Evaluation procedure}

The evaluation was conducted by domain experts with extensive knowledge of both Sovelia Core functionality and PLM workflows. These evaluators include a product manager, a senior application engineer, and a product expert responsible for Sovelia Help documentation. Their combined experience of over 30 years of PLM system, particularly expertise with Sovelia Core, allows for comprehensive assessment from multiple perspectives, covering strategic product considerations, practical implementation challenges and detailed documentation accuracy.

Responses evaluated were generated during the technical performance testing described in Section~\ref{sec:technical-performance-results}, where 30 queries were submitted to the RAG system under realistic load conditions using the test environment detailed in Section~\ref{subsec:test-environment}. This approach ensures that evaluated responses reflect actual system behavior under operational conditions rather than idealized single-query scenarios. Each query produced a generated answer with cited source documentation, which was captured along with performance metrics. The model used to generate responses for expert evaluation was the OpenAI GPT-5 Nano via OpenAI's API, representing a cloud-based proprietary LLM deployment configuration.

The evaluation process employed a structured web-based form presenting each question alongside its generated response and cited sources. For each of the 30 question-answer pairs, evaluators assessed all four dimensions (factual accuracy, relevance, source attribution, completeness) using the 5-point Likert scale. The evaluation form also provided a free-text comment field for each question, enabling evaluators to document specific observations, identify particular strengths or weaknesses, and note examples of errors or exemplary responses.

This structure aligns with domain studies that combine scalar ratings with qualitative comments or interviews to capture issues not visible in aggregated scores \parencite{namLoRATunedMultimodalRAG2025}. In this work, qualitative comments were used to find common areas of failure (e.g., documentation gaps, missing steps, or unsupported claims), which aims to support iterative improvement of both the retrieval pipeline and the underlying documentation quality.

For each question, evaluators read the generated response, verified factual claims against official documentation (and system behavior when needed), and checked whether cited sources supported the response content. Relevance and completeness were assessed based on how well the response matched the question intent and whether it provided sufficient information. Each dimension was scored from 1 (very poor) to 5 (excellent), with optional qualitative comments used to record notable strengths and weaknesses.

Evaluators completed the assessment independently, minimizing bias and ensuring diverse perspectives. The web-based form facilitated systematic data collection, with responses exported as structured JSON data for later quantitative analysis.

\subsection{Technical performance metrics}
\label{subsec:technical-performance-metrics}

Technical performance evaluation quantifies operational characteristics of the RAG system under realistic load conditions using the test environment described in Section~\ref{subsec:test-environment}. These metrics provide insight into system scalability, resource requirements, and user experience quality from a performance perspective. Special attention is given to latency, throughput, and token consumption, which are main contributing factors in practical deployments of RAG systems.

In contrast to evaluation setups where response quality is assessed using similarity-to-reference metrics (e.g., ROUGE-L or embedding similarity) \parencite{namLoRATunedMultimodalRAG2025}, this thesis prioritizes operational measurements (latency, tool usage, token consumption) and expert assessment against documentation sources. Similarity-based metrics require well-defined ground-truth answers, which are often unavailable or ambiguous in enterprise documentation questions, and may not reflect whether a response is supported by the cited sources. Additionally, while response speed is sometimes assessed via user satisfaction ratings \parencite{namLoRATunedMultimodalRAG2025}, it is measured directly in this thesis through end-to-end latency metrics. This is to get rough understanding of how the system would perform in real-world usage scenarios before it's first actual customer deployment.

The implemented system employs a tool-augmented, tool-calling architecture where the language model determines whether to invoke retrieval tools, may execute multiple retrieval operations, and synthesizes responses from gathered context. Performance measurement captures timing data for tool execution (including query embedding, vector search, BM25 reranking, hybrid scoring, and chunk grouping), embedding generation (reported separately to isolate embedding performance), and LLM inference. LLM inference is measured for both the tool decision phase and the response generation phase, reflecting the two-step structure of the tool-calling workflow \parencite{plaatAgenticLargeLanguage2026}.

Performance data is captured through PostgreSQL stored procedures that measure elapsed time for each component and persist measurements to the \texttt{AIChatPerformance} table. Detailed metrics including tool call counts, LLM call counts, individual operation timings, and retrieval pipeline stage breakdowns are stored in a JSONB column for granular analysis. Total query latency represents the sum of all tool executions and LLM calls, providing an end-to-end user experience metric. Token usage statistics are extracted from LLM response metadata and logged to the \texttt{AIChatHistory} table, enabling cost analysis and context window utilization assessment.

For the documentation pipeline, metrics focus on content extraction from Document360 \parencite{Document360API, SoveliaHelp}, Umbraco \parencite{UmbracoCMSDocumentation2025, ReleaseNewsAll} and set of internal PLM documents. Chunk embedding time, and processing throughput (documents and chunks processed per unit time) are measured to evaluate pipeline efficiency and scalability These metrics aim to provide quantitative insight into system performance characteristics and identify potential bottlenecks. All this can be used later to inform infrastructure sizing decisions for production deployments.

\section{Expert evaluation results}
\label{sec:expert-evaluation-results}

Expert evaluation of RAG system responses demonstrates strong overall performance across all four assessment dimensions, with mean scores ranging from 4,31 to 4,49 on the 5-point Likert scale (Table~\ref{tab:evaluation-summary}). These values are comparable in magnitude to prior domain evaluations reporting high overall user satisfaction (e.g., 4,4/5) for technical manual question answering systems \parencite{namLoRATunedMultimodalRAG2025}. This corresponds to quality ratings between ``Good'' and ``Excellent'' on average, indicating that the system produces responses of sufficient quality for operational use in PLM documentation support scenarios. All dimensions exhibited median scores of 5,0, revealing a positive skew in the distribution with most responses achieving the highest rating. Standard deviations between 1.01 and 1.15 indicate moderate variability, with most responses concentrated at high quality levels while a subset demonstrated room for improvement.

Source attribution achieved the highest mean score (4,49), reflecting the system's consistent provision of documentation references with generated responses. Factual accuracy (4,36) and completeness (4,32) received nearly identical ratings, suggesting that responses typically provide correct information with appropriate breadth and depth. Relevance scored marginally lower (4,31), indicating occasional instances where responses included extraneous information or did not fully align with the specific query intent. One potential reason for this is the fixed number of retrieved documents (five) per query, which may lead to inclusion of less relevant context in some cases. No additional filtering or ranking of retrieved documents was performed beyond the initial vector similarity and BM25 reranking stages, which could be an area for future improvement to enhance relevance. However, the overall narrow range between dimensions (0.18 points) demonstrates balanced performance, with no single dimension exhibiting substantial weakness relative to others.

\subsection{Variation across evaluators}
\label{subsec:evaluator-variation}

Analysis of evaluation scores by individual expert reveals notable consistency in rank ordering but systematic differences in absolute rating levels (Table~\ref{tab:evaluation-by-evaluator}). The product expert assigned the highest ratings across all dimensions (4,50--4,83), followed by the senior application engineer (4,40--4,63), with the product manager providing the most conservative assessments (3,80--4,07). This pattern persisted consistently, with the product manager scoring every dimension approximately 0,6--0,8 points lower than the product expert.

These evaluator differences likely reflect variation in assessment stringency rather than fundamental disagreement about response quality. The product manager's role emphasizes critical evaluation of customer-facing information and sensitivity to potential user confusion, possibly leading to more conservative quality assessments. The product expert's deep technical knowledge may enable recognition of subtle correctness that appears less evident to evaluators focused on practical usability. The product expert is also the one maintaining the Sovelia Help documentation \parencite{SoveliaHelp}, so they are most likely to be aware of the areas where the actual source information is lacking or incomplete. The senior application engineer's intermediate position and vast experience in manufacturing field reflects balanced consideration of both technical accuracy and practical utility. This deviation could also stem from differing expectations about what constitutes an ``excellent'' response, with some evaluators applying stricter criteria for top ratings. Since evaluations are inherently subjective, some degree of inter-evaluator variability is expected.

Despite absolute rating differences, evaluators demonstrated strong agreement on relative response quality, with problematic responses consistently receiving low scores from all evaluators and high-quality responses rated favorably across all the evaluators. This consistency in ranking validates the evaluation framework's ability to identify genuinely strong and weak responses independent of individual evaluator calibration.

\subsection{Performance by question category}
\label{subsec:performance-by-category}

Examination of evaluation scores by question category reveals some variation in system performance across different query types (Table~\ref{tab:evaluation-by-category}). Troubleshooting queries achieved the highest scores across all dimensions, with mean ratings between 4,78 and 4,89. Feature inquiries also performed well, scoring between 4,44 and 4,67. In contrast, procedural questions exhibited notably lower performance, with mean scores ranging from 3,61 to 4,00.

This pattern reflects fundamental differences in how documentation addresses different information needs. Troubleshooting content typically appears in dedicated help articles that directly address specific problems with clear explanations, making retrieval straightforward and generation accurate. Feature inquiries benefit from well-structured reference documentation in Sovelia release notes that describe capabilities and specifications of different versions comprehensively. Procedural content, however, often requires synthesis across multiple documentation sections, with steps distributed throughout different articles or implied rather than explicitly stated. The system's fixed retrieval window of five documents may not capture all necessary procedural steps, leading to incomplete or partially incorrect workflows. Additionally, the used model, OpenAI GPT-5 Nano, may struggle to break down complex procedures into clear, sequential steps when source information is fragmented and needs multiple queries to cover completely. This can be potentially alleviated via prompt engineering (instructing the model to do multiple tool calls when necessary) or by increasing the number of retrieved documents, but these strategies were not explored in this evaluation.

Version-specific questions achieved moderate performance with scores between 4,17 and 4,44. Integration questions scored similarly, ranging from 4,22 to 4,56. Both categories face challenges related to information distribution across multiple documentation sources and potential version mismatches where recent features appear in release notes but lack detailed coverage in primary help documentation. One identified problem in the documentation is the fact that Sovelia Help articles lack the information about which version of Sovelia Core they apply to, making it difficult for the retrieval system to answer version-specifically. This limitation likely contributed to occasional retrieval of outdated or irrelevant information for version-specific and integration queries.

\subsection{Question-level results}
\label{subsec:question-level-results}

The question-level results (Table~\ref{tab:evaluation-detailed}) show that many questions were answered consistently well across evaluators. Perfect or near-perfect scores were observed for several troubleshooting queries such as Q3.2 (promotion to In Production), Q3.4 (missing 3D viewer option), and Q3.5 (cancelling or refining search). These questions are narrow in scope and typically have direct documentation coverage, which supports high accuracy and completeness.

Similarly strong results were achieved for several feature and version questions that align with well-defined documentation topics. Examples include Q1.2 (automatic revision increments), Q1.4 (difference between Product documents and general Documents), Q4.3 (when drag and drop was introduced), and Q4.6 (measure functionality in the 3D viewer and when it was added). In qualitative feedback, responses to Q4.6 were described as using multiple resources to gather the information, which suggests that the retrieval pipeline and synthesis worked well when the required evidence existed across documents.

The weakest results were concentrated in a small set of questions where either documentation coverage was limited or retrieval introduced misleading context. Q2.3 (adding components to a bill of materials structure) received low scores (2,3--2,7 across dimensions). Qualitative comments indicate that the response mixed concepts with Equipment BOM and omitted common interaction methods such as drag and drop, which reduced relevance and perceived correctness. Further analysis reveals that retrieved documents did not include the most relevant procedural articles, leading to incomplete synthesis. Q4.5 (which version introduced the commenting feature) received the lowest averages (2,3 across all dimensions), with the introduced version missed entirely due to missing version context in help documentation.

Moderate weaknesses appeared in questions where multiple valid workflows exist but only one was presented. For Q2.1 (releasing a document for manufacturing), feedback noted that the answer focused on an ECO-based workflow, though releases do not necessarily require an ECO. For Q2.6 (exporting a BOM structure to Excel), reporting functionality was expected but not mentioned. Similar issues affected Q2.4 (cloning an item structure, where the normal clone tool was expected). These outcomes point to missing practical workflow detail in the retrieved sources, with the system unable to reflect common alternatives used in practice.

Version and release context proved a clear source of failure. In Q4.2 (changes to search in the latest release), the response presented an older version as the latest with incorrect change claims. These failures stem from help articles lacking version information and the difficulty of finding the latest changes in release notes using only semantic similarity with a limited retrieval window. Q1.5 (supported file formats for conversion to PDF) and Q1.3 (available reports) were explicitly linked to missing information in available documentation rather than retrieval failure.

Some high-scoring questions showed presentation issues without affecting factual accuracy. For Q4.1 (what is new in version 25.1) and Q4.4 (reporting improvements), content was useful but structure was slightly off, indicating that underlying retrieval and synthesis remained effective. Q1.1 (available lifecycle states) was flagged for an incorrect final state despite acceptable aggregate scores, suggesting that small inaccuracies in enumerations may be difficult for non-expert users to detect. Finally, Q5.6 (creating ECOs from the Inventor CAD Add-in) highlighted a coverage limitation: relevant information existed on an external release news page but was not included in the evaluated source set, confirming that system completeness depends entirely on the provided document corpus.

\section{Technical performance results}
\label{sec:technical-performance-results}

Performance evaluation was conducted using the 30-question evaluation set described in Section~\ref{subsec:expert-evaluation-design} on the test environment detailed in Section~\ref{subsec:test-environment}. To assess the practical trade-offs between local open-source and cloud-based proprietary language models, performance testing was conducted using two different LLM providers: OpenAI's GPT-5 Nano via API and GPT-OSS-20B running via Ollama. These LLMs were selected, since they are relatively comparable across intelligence, speed, and context window size \parencite{artificialanalysisGPT5NanoHigh}, but represent proprietary cloud-based and open-source on-premise deployment models respectively. Both configurations utilized the same local Nomic Embed Text model for query and document embeddings, ensuring that observed differences reflect LLM provider characteristics rather than embedding model variations. The test environment consisted of simulated concurrent load with queries executed in a realistic, although scripted, usage pattern. Performance data was collected through PostgreSQL stored procedures and logged to dedicated performance tables. All the numbers shown in this section are rounded to one decimal place for improved readability. Complete numerical results with more decimal places and millisecond accuracy are provided in Appendix~\ref{app:performance-tables}.

\subsection{Overall latency characteristics}
\label{subsec:latency-characteristics}

Query latency measurements reveal substantial performance differences between cloud-based and on-premise GPU-accelerated LLM deployments (Table~\ref{tab:latency-distribution}). The OpenAI configuration achieved a mean total latency of 25,9 seconds with a median of 22,8 seconds and 95th percentile of 40,2 seconds. In contrast, the Ollama deployment on dedicated GPU infrastructure exhibited a mean latency of 91,4 seconds with median of 92,4 seconds and 95th percentile of 163,7 seconds. This represents approximately a 3,5$\times$ difference in end-to-end query response time, with the on-premise deployment consistently slower across all percentiles despite access to enterprise-grade GPU resources.

The latency distribution demonstrates relatively stable performance for the OpenAI configuration, with the 95th percentile remaining under 41 seconds. The Ollama configuration shows greater variability, with the 95th percentile approaching 2,7 minutes. This performance difference persists despite access to substantial GPU infrastructure (4$\times$ NVIDIA L40S GPUs, 192 GB VRAM total), though Ollama's architecture utilizes only a single GPU at a time rather than distributing inference across multiple devices. Most likely causes for slowness include this single-GPU limitation, model architecture efficiency differences between GPT-5 Nano and GPT-OSS-20B, optimizations in OpenAI's inference serving infrastructure and possibly small difference in network latency between the application server and remote GPU infrastructure. More sophisticated inference engines such as vLLM \parencite{umeshOllamaVsVLLM2025} offer better multi-GPU parallelization and optimization strategies that could substantially improve on-premise deployment performance beyond what Ollama's architecture permits. Use of vLLM could be more appropriate for production deployments requiring lower latency and higher throughput across multiple concurrent users. \parencite{umeshOllamaVsVLLM2025}

Both configurations exhibited similar tool-calling patterns, with average tool call counts of 1,30 (Ollama) and 1,33 (OpenAI) and average LLM call counts of 2,30 for both providers. This consistency indicates that the observed latency differences reflect raw computational performance characteristics rather than differences in reasoning behavior or retrieval strategy between the two models.

\subsection{Pipeline stage contribution}
\label{subsec:pipeline-stage-contribution}

Analysis of latency distribution across pipeline stages reveals that LLM inference dominates total query time for both configurations (Table~\ref{tab:stage-contribution}). The OpenAI configuration allocated 99,54\% of total latency to LLM processing, with query embedding consuming 0,36\% and tool execution (including retrieval) accounting for 0,41\% of total time. The Ollama configuration showed an even more pronounced concentration with 99,87\% attributed to LLM processing, with embedding generation and tool execution each contributing less than 0,1\% due to the substantially longer LLM inference times.

The absolute times for embedding generation and tool execution proved comparable between providers. Query embedding generation averaged 61 milliseconds for Ollama and 80 milliseconds for OpenAI, demonstrating that both configurations achieved similar performance for this CPU-bound operation on the local development workstation, as they should. Slightly longer embedding time for OpenAI generated queries could stem from GPT-5 Nano's longer generated search prompt compared to GPT-OSS-20B, requiring slightly more tokens to be embedded. Tool execution time (which includes embedding generation within the retrieval tool) averaged 79 milliseconds for Ollama versus 93 milliseconds for OpenAI, further confirming that retrieval pipeline operations perform consistently regardless of LLM provider selection.

This stage contribution analysis confirms that LLM inference optimization represents the primary opportunity for latency reduction, as retrieval and embedding operations contribute negligibly to total query time. The 3,5$\times$ performance difference between providers manifests almost entirely in the LLM processing stage.

\subsection{Retrieval pipeline performance}
\label{subsec:retrieval-pipeline-performance}

Detailed analysis of the retrieval pipeline reveals that all components perform efficiently and comparably across provider configurations (Table~\ref{tab:retrieval-stages}). Vector search using pgvector's cosine similarity averaged 15,71 milliseconds for Ollama queries and 11,65 milliseconds for OpenAI queries, demonstrating that database-level retrieval operations remain fast even under concurrent load. BM25 reranking added approximately 1,2 milliseconds (Ollama) and 0,9 milliseconds (OpenAI), while hybrid reranking and chunk grouping operations each contributed less than 0,1 milliseconds.

Total retriever time proved nearly identical between providers, averaging 78 milliseconds for Ollama and 92 milliseconds for OpenAI. This consistency confirms that the retrieval pipeline, including query embedding generation, vector search, reranking, and chunk grouping, performs independently of LLM provider selection. The comparable performance validates the architecture's separation of concerns, where retrieval operations on the application server remain unaffected by downstream LLM inference location.

These results demonstrate that the pgvector extension provides adequate performance for the tested scale (217 chunks across 113 documents), with the complete retrieval pipeline completing in under 100 milliseconds consistently. Database-level operations and embedding generation on CPU-only hardware prove sufficient for responsive retrieval, indicating that optimization efforts should focus on LLM inference latency rather than retrieval pipeline components.

\subsection{Tool-calling behavior and multi-step reasoning}
\label{subsec:agentic-behavior}

The tool-calling architecture implemented in the RAG system exhibited measured multi-step reasoning behavior, though single-tool calls predominated in practice (Table~\ref{tab:tool-patterns}). The Ollama configuration produced multi-tool calls (where the LLM invoked the documentation retrieval tool multiple times before responding) in 23,33\% of cases, while the OpenAI configuration exhibited this behavior in 13,33\% of cases. Maximum tool calls reached 4 for Ollama and 6 for OpenAI within the test set, indicating that models occasionally determined that multiple retrieval operations were necessary to adequately address complex queries.

LLM call patterns reveal the two-phase structure of the tool-calling workflow (Table~\ref{tab:llm-patterns}). The first LLM call (tool decision phase) averaged 37,0 seconds for Ollama and 5,1 seconds for OpenAI, during which the model determines whether to invoke retrieval tools or respond directly. The second LLM call (response generation phase) averaged 42,2 seconds for Ollama and 16,4 seconds for OpenAI, where the model synthesizes retrieved context into the final response. The second-to-first call ratio of 4,85 for Ollama and 3,57 for OpenAI indicates that response generation consistently requires more computational effort than tool decision-making, likely reflecting the greater complexity of context synthesis compared to function calling decisions. The substantial latency difference between providers persists across both phases despite Ollama's access to dedicated GPU infrastructure, again suggesting that model architecture efficiency and inference optimization contribute more significantly to response time than raw computational capacity. Additionally Ollama is not too well optimized for multiple concurrent requests \parencite{umeshOllamaVsVLLM2025}, which may further increase latency under the load of the test setup.

The relatively low incidence of multi-tool behavior (13-23\% of queries) suggests that most queries in the evaluation set could be adequately addressed with a single retrieval operation. This pattern may reflect either the focused nature of the test queries or the model's conservative approach to tool invocation, preferring to generate responses from initially retrieved context rather than iteratively refining retrieval. Another possible reason is  that the document retrieval pipeline works as designed to retrieve the most relevant documents in the first call from test corpus, reducing the need for further retrieval.

\subsection{Token consumption and operational costs}
\label{subsec:token-costs}

Token usage analysis for the OpenAI configuration (Table~\ref{tab:token-cost-summary}) reveals moderate consumption patterns across the 30-query evaluation set. Input tokens totaled 97 471 (averaging 3 249 tokens per query), reflecting the combined size of system prompts, retrieved documentation context, and user queries. Output tokens totaled 53 769 (averaging 1 792 tokens per response), indicating that generated responses were substantive and detailed.

At GPT-5 Nano pricing of \$0,05 per million input tokens and \$0.40 per million output tokens, the total cost for the 30-query evaluation amounted to \$0,03 (\$0,00 for input, \$0,02 for output). This translates to approximately \$0,001 per query, suggesting that API costs for production deployment would remain negligible for typical usage volumes in Sovelia Core's target deployment scenarios. In a enterprise deployment with 1,000 queries per day, monthly costs would approximate \$30 (\$0,001 \times 1000 \times 30 = \$30), which is likely justifiable given the performance benefits observed. However, cost considerations must be balanced against performance requirements, data governance policies, and infrastructure investments.

The Ollama on-premise deployment incurs no per-query API costs, though it requires substantial GPU infrastructure investments (enterprise GPU servers, networking, maintenance) if run locally at scale. However, it's possible to rent dedicated GPU instances from cloud providers trusted by customers to run Ollama models, which introduces variable operational costs depending on instance type, usage patterns, and provider pricing. The observed 3,5$\times$ latency difference between providers despite dedicated GPU infrastructure suggests that cost-performance trade-offs extend beyond simple API cost comparisons to include infrastructure amortization, operational complexity, and performance requirements. Organizations with existing GPU infrastructure, strict data residency requirements, or very high query volumes may find on-premise deployment economically viable despite performance limitations, while those prioritizing responsiveness and minimizing infrastructure complexity may justify API costs for cloud-based models.

\section{Implications for RAG system design in PLM contexts}
\label{sec:implications-plm-rag}

Beyond the Sovelia Core case, these results provide an empirical point of reference for PLM research on how RAG systems behave when integrated into operational PLM environments. The findings highlight which constraints tend to dominate in practice (documentation completeness, version context, and access control) and which factors are secondary at typical scales (retrieval latency and embedding overhead). This supports further research and development on AI-assisted PLM knowledge work by grounding design choices in observed behavior rather than only conceptual architectures.

The results suggest that the primary determinant of response quality is the availability and structure of source documentation. Most questions achieved high scores with strong source attribution, which indicates that the system can reliably summarize and cite what exists in the corpus. When answers were weak, the issues often matched gaps in the available sources or missing workflow details, especially in procedural questions such as releasing documents, exporting structures, and adding BOM components.

The category analysis shows that troubleshooting queries performed best, while procedural questions performed worst. This difference is important for PLM deployments, because procedural questions are common in onboarding and daily work. For this reason, production deployments should not only focus on retrieval and model configuration, but also on ensuring that key workflows are documented in a consistent and complete way. Where multiple valid workflows exist, documentation should make the alternatives explicit. Without this, even a well-performing RAG system may appear incomplete or misleading.

Version-specific queries highlight an additional requirement: version context must be available in the retrieved sources. Several qualitative comments indicate failures where older information was presented as current, or where the wrong release version was cited. This is consistent with the limitation that many help articles do not include explicit version applicability. A practical mitigation is to add version metadata to documents during ingestion and to store it alongside chunks. The retrieval and prompting logic can then filter or prioritize content based on the user's target version.

Procedural weaknesses also suggest that the system should more often take a multi-step approach. When the retrieved context is incomplete, the model could either call retrieval again with a refined query or ask a brief clarifying question. Both strategies are compatible with enterprise constraints because they keep grounding in the documentation corpus, but they require explicit tool-calling instructions and possibly a larger retrieval window for complex tasks.

From an infrastructure perspective, LLM provider selection proved the dominant factor in query latency. The cloud-based configuration (OpenAI GPT-5 Nano) produced approximately 3,5$\times$ faster responses than the on-premise open-source configuration (Ollama GPT-OSS-20B) despite access to enterprise-grade GPU resources. This difference reflects the combined effects of single-GPU utilization in Ollama, inference optimization differences, and network latency. Ollama is therefore not well suited for low-latency deployments under concurrent load in its current form, and more sophisticated inference engines such as vLLM \parencite{umeshOllamaVsVLLM2025} should be considered for production use requiring lower latency and higher throughput. Azure OpenAI \parencite{mrbullwinkleWhatAzureOpenAI} represents a potential middle ground, providing more control over data residency compared to OpenAI's public API, though it was not tested in this evaluation.

Retrieval and embedding operations contributed minimally to total latency at the tested scale, with similarity search and reranking completing in under 100 milliseconds consistently. Tool-calling overhead remained limited, with multi-step retrieval observed in only 13--23\% of queries. This confirms that deployments should prioritize LLM serving choices and inference optimization over further retrieval complexity. Hybrid cloud-local deployment remains practical, as embedding and retrieval can remain on-premise while LLM inference is selected based on policy and latency requirements.

Cost considerations depend primarily on the chosen LLM deployment model. Cloud APIs provide low per-query cost with lower latency, while on-premise deployments avoid API costs and retain data control at the expense of higher latency and infrastructure complexity. Organizations must weigh these trade-offs based on performance requirements, data governance policies, and existing infrastructure investments. For typical Sovelia Core deployment scenarios with moderate query volumes, cloud API costs remain negligible (approximately \$0,001 per query), making performance and governance considerations more critical than direct operational costs.

Finally, the evaluation suggests that improvements should be targeted where they provide the most value. For response quality, the highest leverage comes from improving documentation coverage for procedural and versioned topics. For system responsiveness, the highest leverage comes from improving LLM inference performance, for example by choosing a faster provider or a more optimized on-premise inference framework. This however needs to be balanced against cost, data governance, and infrastructure complexity considerations so there is no one-size-fits-all solution for all organizations.
